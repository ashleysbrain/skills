# IP Encryption Protocol for External-Facing Organism Content

## Purpose

When producing ANY external-facing work derived from the DS organism (courses, marketing, public docs, open-source releases, conference talks, blog posts), the biological isomorphism architecture must be encrypted behind technology analogs. This document defines the full 5-layer defense model, proven on the L&D curriculum panel deployment (2026-07-02).

This expands `biological-abstraction-framework.md` beyond skill releases to cover ALL external content types.

## The Reverse-Engineering Paradox

The core tension: transparency requirements (runnable code, benchmarks, real system examples) directly conflict with IP protection. The more honest and complete the external content, the more the proprietary architecture leaks.

A sophisticated competitor can reconstruct the biological architecture from:
1. The module/course structure (if it mirrors tissue types)
2. Exercise code (if it implements real routing or scoring patterns)
3. The integrated system view (if all components are shown together)
4. The scoring mechanism (if the real algorithm is demonstrated)

Resolution: layered defense. No single layer is sufficient. All five must be active.

## Layer 2: Black-Box Exercises

Students/consumers interact with pre-built components through APIs. They see inputs and outputs. They do NOT see internal routing logic, the scoring engine, or the specialist dispatch mechanism. They learn to USE the patterns without seeing the production implementation.

This satisfies partial learning goals but conflicts with full code-transparency requirements.

## Layer 3: Toy Implementation Separation

External content teaches patterns using SIMPLIFIED toy implementations that demonstrate the concept through DIFFERENT mechanisms than the production system. The real system uses biological isomorphism. The external content uses naive implementations that achieve similar pedagogical results through standard engineering.

Students learn the concept. They do not get the engine.

## Layer 4: Crown Jewel Protection

Identify the crown jewels of the proprietary system. These are the algorithms or mechanisms that, if revealed, would let a competitor reconstruct the full architecture.

**Proven crown jewels (from L&D panel 2026-07-02):**
- The info_gain estimation algorithm (the scoring mechanism at the heart of the decision gate)
- The specific combination of physics plus biology (the compound moat)
- The organism topology (40+ engines, specific assignments, tissue connectivity)
- The proprietary 8D/TWC scoring formula

Crown jewels are addressed CONCEPTUALLY (what they are, why they matter, how to think about them) with SYNTHETIC benchmark data showing impact. NOT with working implementations of the actual algorithms. Teach the problem, not the solution. This is the one place where "no runnable code" is the right answer.

## Layer 5: Cohort NDA (Premium Tiers)

For high-value, small-group interactions (cohort courses, enterprise training, advisory engagements), require an NDA covering reference implementations and detailed architecture discussions. Standard for premium technical training where proprietary methods are taught.

## Pre-Publication Reverse-Engineering Checklist

Run before ANY external material ships:

- [ ] No references to specific biological systems (nervous, cardiovascular, immune, digestive, etc.)
- [ ] No scientist names associated with specific engines
- [ ] No body-part analogies (thalamus, hippocampus, vagus nerve, etc.)
- [ ] No references to tissue types
- [ ] No references to our specific engine topology (port numbers, engine count, service names)
- [ ] No references to proprietary scoring formulas
- [ ] All code examples use naive implementations, not production code
- [ ] All examples use standard software engineering vocabulary
- [ ] Module/course/content structure does NOT mirror the biological architecture (reorganize if it does)
- [ ] Exercise code does NOT reveal routing or scoring patterns through implementation
