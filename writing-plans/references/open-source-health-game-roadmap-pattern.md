# Open-Source Health-Game Roadmap Pattern

Session-derived notes for planning a science-based health product with an open-source community layer and a premium hosted moat.

## Core release shape
- Release the *community standard* openly so the methodology can spread.
- Keep the *hosted intelligence / personalization / premium UX* proprietary.
- Make the open layer actually useful, not a teaser.
- Put the boundary in the roadmap itself, not just in marketing copy.

## Build order for scale
1. Define the first user, first health outcome, and first channel.
2. Build baseline + evidence capture before adding game loops.
3. Persist native scores, confidence, and drift history.
4. Add the smallest useful daily loop.
5. Expand into streaks, quests, rewards, and adaptive difficulty.
6. Open-source the standard once the core loop is stable.
7. Add premium predictions, partner workflows, and enterprise surfaces.

## Scale pattern
Use a middle-out model:
- start with one user and one daily loop
- strengthen the core engine and open standard
- expand upward into teams, providers, and enterprise
- expand outward into templates, integrations, partners, and API consumers
- keep every new surface compatible with the same core method

## Product-design guardrails
- Health first, game second, monetization third.
- Reward consistency, recovery, and agency.
- Avoid shame mechanics, addiction loops, or coercion.
- Compare users to their own baseline before any broader benchmark.
- The game layer should amplify adherence and insight, not replace the health engine.

## Revenue ladder
- Free community standard
- Paid consumer pro tier
- Premium hosted intelligence
- Enterprise / API / partner offerings
- Services, templates, and implementation support

## Useful phrasing for docs
- "open-source variation"
- "community standard vs premium moat"
- "compounding productivity after launch"
- "middle-out scaling"
- "science-based health game"
- "the product should be usable, extensible, and economically scalable from day one"
