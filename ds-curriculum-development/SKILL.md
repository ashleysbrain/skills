# the specialist engine

Build educational courses and training programs derived from the proprietary DS organism architecture. Translates internal system knowledge into teachable material while protecting proprietary IP through layered defense and a dialectic validation loop.

## When to Use

- User asks to build courses, training programs, or educational content based on DS systems
- User wants to teach others how to build physics-informed AI agents
- User wants to monetize the organism's architecture through educational products
- User asks for an L&D panel, curriculum roadmap, or course module breakdown
- User wants curriculum reviewed through adversarial panels and multiple iterations

## Prerequisites

- Deep dive into the source system (organism architecture, engines, agents) must be completed BEFORE curriculum design begins
- Load `advisor-panel-orchestration` skill for the L&D panel execution
- Load `da-vinci-creative-process` skill for PDF rendering of curriculum artifacts
- Load `adversarial-strategy-stress-testing` skill for the adversarial review protocol

## How to Run

### Phase 0: Deep Dive (Before Panel)
1. Read the source system architecture (ENGINE_REGISTRY.yaml, physics_gate.py, sherman_router.py, methodology files)
2. Identify what is genuinely different from standard AI agent frameworks (AutoGPT, LangChain, CrewAI)
3. Map each differentiator to a teachable concept
4. Document the findings as the source material for curriculum design

### Phase 1: Encryption Layer (IP Protection)
Before any curriculum design, build the encryption map. This is the IP protection layer.

**CRITICAL: The encryption map is INTERNAL ONLY. It must NEVER appear in any public document.** The Round 1 adversarial panel found that the roadmap itself was the biggest IP leak because it contained the encryption map, the Rosetta Stone translation table, and the reverse-engineering checklist all in one public-facing document.

1. List every proprietary concept, architecture pattern, and internal name
2. For each, define a PUBLIC technology analog that is functionally equivalent but obscures the proprietary source
3. Create an internal-only mapping document (never published, never in course repos, never in the public roadmap)
4. STRUCTURALLY REDESIGN the public course architecture so it does NOT mirror the internal system. Change category counts, topology, framing. Renaming terms is NOT enough. The structural pattern must be different.
5. Run the reverse-engineering checklist before any material ships

**The encryption paradox:** Pedagogical requirements (runnable code, benchmarks, real systems) directly conflict with IP protection. The more honest and complete the course, the more IP leaks. Resolution: layered defense.

| Defense Layer | What It Does | Failure Mode |
|---|---|---|
| Terminology firewall | Course material uses standard engineering terms, never proprietary names | Cosmetic only. Architecture can be reverse-engineered from operational behavior even with renamed terms. |
| Black-box exercises | Students interact via APIs, never see internal routing/scoring logic | API response format leaks internal architecture through execution traces. Sanitize API responses to contain ONLY: task_id, result, cost, latency, success/fail. |
| Toy implementations | Course uses naive implementations via different mechanisms than production | If toy implementations achieve similar results, they ARE the competing product. The gap between toy and production IS the value proposition. |
| Crown jewel protection | Proprietary scoring/estimation algorithms taught conceptually only | The concept space is defined even without the algorithm. Competitors know WHAT to build, just not HOW. |
| Access-based protection (replaces NDA) | Hosted reference system with server-side crown jewels, time-boxed API credentials, alumni subscription | Knowledge exit is unstoppable. Students who understand the approach can describe or reimplement it. |

**NDA is NOT effective for course content.** Cost asymmetry ($50K-200K enforcement vs $2.5K-4K revenue), scope ambiguity, the review problem, and enrollment friction make NDAs practically unenforceable. Use access-based protection (the AWS/Stripe model) instead.

### Phase 2: Dialectic Validation Loop (MANDATORY)

The user requires multiple iterations of review from writing panel to adversarial panel and back until consensus, then cross-model review. This is a binding workflow.

**Full loop structure:**
```
Round 1 Advisory Panel (5+ seats): Produce initial design
    ↓
Round 1 Adversarial (4+ seats): Attack the design, find critical issues
    ↓
Synthesize: Consolidate all adversarial findings into attack report
    ↓
Round 2 Writing Panel (3+ seats): Address every finding, revise the roadmap
    ↓
Round 2 Adversarial (same seats): Re-attack the revised version
    ↓
Convergence Check: Compare R1 vs R2 findings. Issues resolved or recurring?
    ↓ (if resolved → proceed)
    ↓ (if recurring → Round 3)
Round 3 Integration: Build single clean master document, resolve contradictions
    ↓
Cross-Model Review: Different model does blind review with no context
    ↓
Final: Render to PDF, deliver
```

**Proven advisory roster for curriculum development (2026-07-02, validated across 2 rounds):**
- Instructional design and learning science (chunking, spaced repetition, interleaving)
- AI agent architecture and technical rigor (demands runnable code, contrastive demonstrations, failure mode coverage)
- Platform and credentialing strategy (LMS, GitHub, auto-grading, pricing)
- Market positioning and pricing philosophy (who buys, why they buy, what makes it uncopyable)
- Physics-to-practice bridge (how to make hard concepts accessible)
- Adversarial seat MANDATORY in every round

**Proven adversarial roster (4 seats, different from advisory):**
- The Competitor: attacks IP theft, market undercut strategy, reverse-engineering timeline
- The Target Buyer: attacks purchase probability, pricing reality, missing content, free competition
- The IP Auditor: attacks document leaks, structural fingerprints, NDA enforceability
- The Curriculum Destroyer: attacks pedagogical soundness, completion rate, learning path design

**Convergence criteria:** The loop stops when the adversarial panel cannot find NEW critical findings. Recurring issues are acceptable only if they are acknowledged tradeoffs (e.g., "instructor credibility requires a real person, not a panel fix"). When all remaining issues are execution failures (revisions not applied to master document) rather than design failures, the design has converged.

**Cross-model review:** Dispatch the final consensus version to a different model entirely (DeepSeek, Gemini, Grok). The model gets the document blind with no context about who produced it or what panels ran. Fresh pattern recognition, no anchoring.

### Phase 3: Post-Synthesis Integration (CRITICAL PROCESS STEP)

The Round 2 writing panel produces revisions as SEPARATE DOCUMENTS. These must be integrated into a single clean master document. This is the #1 process failure from the 2026-07-02 session: all four adversarial seats independently found that revisions existed on paper but were never applied to the master.

**Integration checklist:**
- [ ] Read ALL revision documents produced by the writing panel
- [ ] Build a NEW master document from scratch (do NOT patch the old one line-by-line)
- [ ] Resolve ALL contradictions between revision documents (course counts, pricing, structures)
- [ ] Remove ALL biological references, scientist names, encryption maps, Rosetta Stone tables
- [ ] Verify zero proprietary terms via search before publishing
- [ ] Run the reverse-engineering checklist against the final document

### Phase 4: Phased Development
Ship ONE course as proof of concept before building the full program.

1. Build the benchmark repo and sandbox API FIRST (gives buyer evaluation path)
2. Build the free on-ramp module (Course 0, teaches commodity skills, REQUIRED prerequisite via readiness check)
3. Build the proof-of-concept course (the one that proves the core thesis)
4. Gate: the course must pass three tests before further development:
   - Runnable code test: `python demo.py` works and shows the concept in action
   - Contrastive demonstration test: learner reproduces a failure mode without the concept, then with it, and observes the qualitative difference
   - Hard failure mode test: deadlocks, cost explosions, cascading failures all handled

### Phase 5: Production Pipeline
Per module production sequence:
1. Content draft (the specialist engine: voice, AI-tell removal)
2. Exercise design (the specialist engine: scenario, lab)
3. Template design (the specialist engine: visual, layout)
4. Render (the specialist engine: PDF, HTML, interactive)
5. Pacing review (the specialist engine: rhythm, flow)
6. Quality gate (the specialist engine: educational and art-direction quality)
7. Encryption check (no biological fingerprints)
8. Technical rigor check (runnable code verified)
9. Final sign-off

## Quick Reference

### Branding (REVISED — Physics Dropped)

**CRITICAL: The "Physics-Informed" branding is a LIABILITY, not an asset.** All four Round 1 adversarial seats independently concluded the physics framing hurts more than it helps. Sophisticated buyers (staff engineers) see through decorative physics vocabulary. The Emperor's New Clothes attack destroys credibility.

**Current branding:** "Production-Grade AI Agent Engineering." Makes production claims (verifiable via benchmarks, sandbox), not physics claims (puncturable). Physics concepts survive INTERNALLY under standard engineering names:
- Free Energy → "Cost-Aware Decision Filters"
- Critical Slowing Down → "Early Warning Signals"
- Superposition → "Parallel Decision Paths"
- Adiabatic → "Incremental Change and System Stability"
- Entanglement → "Typed Contracts and State Propagation"

### Course Structure (REVISED — Lifecycle Based)

4 courses organized by engineering lifecycle (NOT topic-based, NOT mirroring internal architecture):
- Course 0: Building Foundations (FREE, required prerequisite)
- Course 1: Design — Building Specialist AI Services
- Course 2: Build — Intelligent Task Routing and Decision Architecture
- Course 3: Operate — Multi-Agent Coordination and Health
- Course 4: Harden — Adversarial Testing and Resilience

**The lifecycle structure (Design → Build → Operate → Harden) deliberately does NOT mirror the internal system architecture.** Different category count, different topology, different framing.

### Module Template (REVISED — 3 Parts, Not 7)

The 7-part workbook template has 90-95% drop-off. Cut to 3 parts:

1. **CONCEPT** (8-10 min): incident hook + worked example + one-line takeaway
2. **BUILD** (15-20 min): scaffolded build with fading support (70% code early, 20% late)
3. **BREAK** (10-15 min): break it, diagnose it, boundary check

Plus: Automated spaced recall (LMS-scheduled, NOT optional — moved from optional to automated after Round 2 correction).
Plus: Boundary reference implementations at each course boundary (clone-and-continue for dropouts).

### Contrastive Demonstrations (REPLACES Synthetic Benchmarks)

Every concept demonstrated via before/after specific failure modes, NOT fabricated percentage improvements. Example: Cost-Aware Decision Filter BEFORE ($340/1000 tasks, 12 rate-limit failures) vs AFTER ($47/1000 tasks, 0 failures). Learner runs both versions.

### Platform Stack (Proven)
- LMS: LearnDash on WordPress (~$300/yr + hosting)
- Code: GitHub Classroom (free) with GitHub Actions CI auto-grading
- Interactive: Google Colab (free) or self-hosted JupyterHub

NOT Coursera or edX (wrong revenue model, wrong audience, wrong tools for code-intensive content).

### Phase 6: Document Versioning (User Standing Rule)

The user does NOT want multiple documents sharing the same name or using generic "final" labels that become ambiguous after the next revision. Version every document the moment a second iteration is produced.

**Naming convention (proven 2026-07-02):**
- Canonical artifacts: `<topic>-v<N>-<descriptor>.md` (e.g., `curriculum-roadmap-v3-final-consensus.md`)
- Panel outputs: `curriculum-panel-r<round>-<descriptor>.md` (e.g., `curriculum-panel-r1-advisory-batch1.md`)
- Adversarial outputs: `curriculum-adversarial-r<round>-<descriptor>.md`
- Revision outputs: `curriculum-r<round>-revision-<domain>.md`
- Cross-model reviews: `curriculum-cross-model-<descriptor>.md`
- Internal-only references: keep descriptive name, mark CLASSIFICATION in header

**ALWAYS create a master index** (e.g., `CURRICULUM-DOC-INDEX.md`) that lists every document with: version, file path, description, and classification (PUBLIC vs INTERNAL ONLY). This is the single source of truth for which document is canonical.

**When renaming existing files**, use `mv` via terminal, not write_file (which would create duplicates). Verify the rename with `ls` after.

**PDFs mirror their markdown counterpart**: `curriculum-roadmap-v3-final-consensus.pdf` matches `curriculum-roadmap-v3-final-consensus.md`.

## Pitfalls

- **Scope creep is the #1 killer.** A full curriculum program is 12-24 months of work. Always scope Phase 1 to ONE course, 25-30 hours, 90-120 days. Prove the thesis before building the program.
- **Revenue projections hallucinate market size.** The addressable market for niche technical courses is 1,000-3,000 people. Budget for 100-200 buyers. Explore B2B licensing as the real revenue multiplier.
- **Physics branding is a liability.** Sophisticated buyers see through decorative physics vocabulary. Drop it from ALL external-facing material. Use standard engineering terms publicly. Physics concepts survive internally under engineering names.
- **The 7-part workbook template has 90-95% drop-off.** Cut to 3 parts (Concept, Build, Break). Make spaced recall automated, not optional.
- **Progressive project dependency creates a cliff.** Missing one course locks learners out. Provide boundary reference implementations at each course entry point.
- **Synthetic benchmark data means fabricated numbers.** Replace with qualitative contrastive demonstrations (real failure mode before/after).
- **The roadmap document itself is the biggest IP leak.** It must NOT contain the encryption map, biological terms, scientist names, or the reverse-engineering checklist. Split into public and private versions.
- **Module structure can leak proprietary architecture.** If courses mirror the internal system, a competitor reconstructs it from the catalog. Use a different organizational pattern (lifecycle-based, not architecture-based).
- **NDA is practically unenforceable for course content.** Use access-based protection instead (hosted system with server-side crown jewels).
- **The master roadmap must be rebuilt from scratch after revisions.** Patching line-by-line produces internally contradictory documents. Build clean.
- **Instructor credibility is the #1 remaining gap.** No name, no GitHub, no track record = "production-grade" is unverified marketing. Requires a real person with verifiable production AI experience before launch.
- **Complex planning documents MUST be rendered to PDF.** The user cannot consume 300+ line markdown documents. No green cover pages for internal docs.
- **The dialectic loop is mandatory.** User requires multiple iterations: advisory to adversarial and back until consensus, then cross-model review. Do not skip rounds.
- **The writing panel produces revisions as separate documents.** These must be integrated into the master. The #1 process failure is revisions existing on paper but never applied.
