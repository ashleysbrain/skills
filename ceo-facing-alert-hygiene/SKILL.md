# principal-Facing Alert Hygiene

## Law
The principal surface shows decisions and outcomes that need a human. Engine state (provider balances, key limits, throttle, retry storms, dead vendor routes with live alternates) is NOT a principal decision — surfacing it daily is a defect, not diligence. A nag the principal has seen twice and not actioned is standing instruction: "we are not actioning this" — the system must record that disposition and stop re-rendering it.

## When an alert fires, before it reaches the principal
1. **Classify**: principal-decision (vendor contract, spend approval, direction change) vs engine-state (quota, balance, throttle, restart). Engine-state never escalates as-is — route it to the internal formulary/budget lanes.
2. **Check for live alternates.** If another provider lane serves the same function, the alert's impact is zero: suppress, note the alternate, done. Only a fully-fenced capability (all lanes dead, no keyless fallback) earns a principal card — and that card carries the bake-off numbers, never a bare question.
3. **Strip vendor language.** Provider error text ("Please recharge.", "Key limit exceeded") is a vendor's word reaching the principal's screen verbatim. Translate to organism terms or drop it.
4. **A 429-only failure signature is throttle, never balance.** Providers return "Insufficient balance... Please recharge" (429-class) under rate and concurrency limits even when the account is funded, so any alert template that says "check provider status/credits" on a 429-only signature manufactures false recharge advice. Verify balances through the provider's balance API or the key-state sentinel before ANY credit-flavored alert fires, and word 429-only alerts as rate/concurrency limits with an explicit do-not-recharge note.
5. **Scheduled QA/verdict organs never deliver raw reports to the principal surface.** When an unscheduled file/report lands in the principal chat (a raw `.md` from a QA seat, a cron verdict dump), the defect is in plumbing, not policy: hunt the emitter chain in order — (a) cron `jobs.json` delivery field on the firing job (unset delivery defaults the report to the origin chat; internal/QA seats need `delivery: local`), (b) the preflight wake-gate that decided the seat should run at all (mtime-based `files-newer` checks count `__pycache__`/`.pyc`/venv churn as WORK, waking the seat with nothing real to gate — noise filters belong INSIDE the preflight scanner, not per-job), (c) the scheduler's default-delivery path. Fix both layers: set explicit delivery on the job AND filter the scanner, then verify by re-running the scanner against the exact path that leaked (must return NO_WORK) — fixing only the delivery leaves the seat burning cycles on bytecode.

## Killing a recurring nag (emitter-chain hunt)
When the same alert resurfaces daily, do not re-dismiss it — find the render loop. Do not solo-hunt: dispatch a read-only forensic subagent (structured output schema: sender + file:line evidence + scheduling mechanism + root cause + kill recommendation) over the log/script fleet in parallel with your own targeted reads, and post the sibling a bus note so both operators cover their own daemons — a sender living on the sibling's surface is invisible to a one-sided grep. Then walk the loop locations:
1. **Bus rows**: query the operator bus (`message-bus.db messages`) for the alert text. A `status='done'` alert that still renders means a digest is re-reading history, not that the alert is live. Stale `pending` rows to `ceo`/`all` are the classic resurfacing pool — close them with an explicit disposition note.
2. **Question-card outbox (BUTTONS specifically)**: Telegram inline buttons come from the tap-to-rule card system (`organism/question_buttons.py` writing append-only `stores/question-outbox.jsonl`), not from cron output or scripts — a grep of jobs.json will come back clean while cards keep re-rendering. Grep the outbox for the alert text, rebuild live-pending state (all `card` events minus those with a later `answered`/`expired` event), and kill zombies by APPENDING an `expired` event per card with a disposition reason — never rewrite or truncate the file; append-only is the module's lifecycle contract, and deleting events re-fires the renderer. Unanswered cards re-render indefinitely: a card whose question has gone moot is the classic zombie button.
3. **Sent-text search**: to find which agent turn actually produced a message, query `<agent-home>/state.db` `messages_fts MATCH '<distinctive text>'` and group `messages` by `session_id` — this is the definitive record of what was composed on a surface; log greps show provider errors, not deliveries.
2. **Digest/brief queries**: the morning-brief and digest code re-select pending bus rows and open ledger decisions each render. A row closed at the source disappears from every downstream surface — always fix the row, never patch the renderer.
3. **Standing decision tasks**: check the task ledger for open `actor_class='human'` rows about the same topic. Annotate or resolve with the principal's actual disposition ("explicitly not actioned, alternates live") so it stops ranking into NEEDS-YOU.
4. **Verify the kill**: after dispositioning, confirm the emitting query no longer returns the row. A suppressed-but-still-rendering alert means the emitter is somewhere else — keep hunting, do not declare victory on the write alone.
5. **Scanner dampener loops (all-night button storms)**: a scheduled scanner that both mints findings AND pages the principal must dampen on ANY ledger state within a lookback window, not just open/claimed/blocked — when the resolution organ lawfully CLOSES a row (exposure healed, fix landed), an open-only dampener reads that as "nobody is handling this" and re-mints + re-pages the identical question every pass, all night. Detection signature: paged question text byte-identical across hours, ledger shows done/closed rows under the same title prefix. Fix set: dampen on any-state rows within N days; page only findings freshly minted this pass; keep the dry-run flag OUT of the pager path. Related invariant rule: a doctrine self-test written against a transient exposure state (asserting a specific violation must exist) goes RED the day the exposure heals — encode the INVARIANT (external binds never silently pass; a loopback bind is the lawful end state), never the current exposure shape.

## Pitfalls
- Never delete evidence: disposition (close + note) preserves the audit trail; deletion looks like loss and re-fires the detector.
- A repeated alert is not escalating urgency — it is usually ONE unclosed row multiplied by a daily render. Count distinct sources before escalating tone.
- Do not write "provider X is dead" anywhere from one lane's failure — exhaustion is per-key/per-lane state, and alternate routes commonly remain live (see multi-provider-credential-routing for route enumeration).
- When the principal explains a nagging surface was deliberately built for accessibility (one-tap cards, ADHD-support decision surfaces), the defect is inaccuracy, not existence: fix the truth gate (verified numbers, stale-card expiry, 429-≠-balance wording) and keep the surface — retiring a purpose-built accessibility mechanism to stop one bad alert destroys the feature to secure it.
- Verification runs must never page: a --dry-run path that still invokes the principal pager leaks diagnostic pages to the real surface while you are hunting the original flood — the leak presents as the very defect under investigation.
