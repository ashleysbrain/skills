# v2.2 Diagnostics-First Pipeline Architecture

**Added:** 2026-07-23
**Purpose:** Reference pattern for building coaching engines where diagnostics actually shape output, not decorate it. Born from the E16 master defect (see SKILL.md).

## The architectural flip

v2.1 ran diagnostics AFTER generation. v2.2 runs them BEFORE. This is the difference between a "diagnostic shell" (decorative metadata) and a "functional engine" (diagnostics shape the coaching).

### v2.1 (BROKEN — E16 defect)
```
v1 classify_situation
  → v1 generate_coaching_guidance (LLM call, no diagnostics)
    → v2 attach diagnostics as metadata
      → output
```
The LLM never sees what the diagnostics found. Every diagnostic output goes to `science_trace`, never to the coaching text.

### v2.2 (FIXED — diagnostics-first)
```
v1 classify_situation
  → v2 assess_complexity (gate: fast vs deep)
    → [if deep] v2 run all diagnostics IN PARALLEL
      → v2 build_directives (synthesizes diagnostic outputs into LLM instructions)
        → v2 LLM call WITH directives in system prompt
          → v2 MAP gate (check motivation/ability/prompt)
            → [if MAP gaps] v2 revise steps (send back to LLM)
              → v2 two-layer output (coaching_response + science_trace)
                → persist session state (history, diagnostics, next_checkin)
```

## Function signature contract

**The smell:** `run_v2_pipeline(coaching_guidance=...)` — accepting pre-generated coaching means diagnostics run AFTER generation by construction.

**The fix:** `run_v2_live(text, classification, history, llm_generate_fn, ...)` — the pipeline OWNS the LLM call. The `llm_generate_fn` is injected as a callable that receives directives in its arguments.

```python
def run_v2_live(
    text: str,
    classification: Dict[str, Any],
    conversation_history: Optional[List[Dict]] = None,
    llm_generate_fn=None,  # callable(text, classification, history, context, directives, voice, model)
    context: str = "b2c",
    voice: Optional[str] = None,
    model_override: Optional[str] = None,
) -> Dict[str, Any]:
```

The `directives` parameter is the critical addition. The LLM generate function must accept directives and inject them into its system prompt BEFORE generating coaching text.

## MAP gate revision loop

The MAP check runs AFTER generation but BEFORE output. If it finds gaps (motivation, ability, or prompt missing), it sends the steps back for revision:

```python
if complexity.path == "deep" and coaching_raw.get("steps"):
    coaching_raw["steps"] = _revise_steps_for_map(
        coaching_raw["steps"],
        diagnostics.get("map_check", {}),
        diagnostics.get("efficacy_calibration", {}),
    )
```

This closes the defect where MAP output was metadata-only. Now MAP gaps actually modify the steps.

## Session state persistence

The pipeline must persist diagnostics across turns. Without this, every interaction starts fresh and the engine cannot learn.

```python
session_state = {
    "history": conversation_history,
    "prior_diagnostics": diagnostics,  # motivation, efficacy, etc. carry forward
    "next_checkin": None,  # set by monitoring loop
    "completed_milestones": _detect_completed_milestones(conversation_history),
}
```

The `_detect_completed_milestones` function scans history for completion signals ("i did", "i finished", "completed") so Progress Checkpoints fire on ACTUAL completion, not on step[0] of a new plan.

## Verification protocol (run before claiming build complete)

For each diagnostic module, answer this question: **does its output reach the LLM prompt, or just the science_trace?**

| Module | Reaches LLM? | How? |
|---|---|---|
| motivation_diagnosis | YES | `directives["autonomy"]` |
| efficacy_calibration | YES | `directives["efficacy"]` (includes first_step_size, stretch_factor) |
| mindset_scoping | YES | `directives["mindset"]` |
| loss_aversion | YES | `directives["framing"]` |
| habit_automaticity | YES | `directives["habit"]` |
| if_then_planner | YES | `directives["implementation"]` + surfaced in next_action |
| map_check | YES (post-gen) | revises steps if gaps found |
| multi_perspective | YES | `directives["voices"]` (when multi-voice) |
| perma_scan | YES (conditional) | `directives["perma"]` (when gated conditions met) |
| progress_checkpoints | YES (post-gen) | acknowledgment text based on completed milestones |

If any module's output appears ONLY in science_trace, it is decorative and the build is incomplete.

## The 34 errors found in the v2.1 audit

Documented so future builds avoid them. Categorized:

**Logic errors:** unreachable code branches, inverted comparisons, dead code paths
**False positives:** substring markers that match their own negation, markers that collide across modules
**Construct gaps:** partial coverage of the underlying science (e.g., Bandura's 4 efficacy sources but only 1 implemented)
**Architecture defects:** diagnostics computed but not wired to generation (the E16 family)
**Naive text processing:** no negation handling, no density normalization, stopword collisions

See the session transcript from 2026-07-23 for the full E1-E34 catalog with fixes.
